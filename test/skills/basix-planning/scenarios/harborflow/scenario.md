# HarborFlow: fictional delivery brief

HarborFlow coordinates tenant-owned shipments from carrier intake through stock, reservation, dispatch and financial settlement. This brief and `source-manifest.json` are invented benchmark inputs. They describe required future behavior, not an implemented system or measured performance. Produce a reviewable delivery plan; do not create the product, branches or 100 placeholder source files during this planning exercise.

## Product boundary and baseline

The target has one pure deterministic engine, shared contracts, shared database adapters and five independently deployable services: ingestion, inventory, allocation, execution and settlement. All five services must use that same engine implementation for domain decisions. The engine must not know about service implementations, database clients, network calls, wall clocks or random generators. Inputs carry the clock, generated identities and policy versions needed to reproduce a decision. TypeScript modules and SQL migrations listed in the manifest are the exact 100 production source files in scope. Their IDs identify source ownership; `work` is a short description and `role` explains responsibility. Tests, fixtures, build configuration, operational configuration, documentation and evidence are necessary auxiliary work where relevant and do not count toward 100. Any proposed additional production module needs an explicit scope decision rather than silently becoming file 101.

`B0` is a symbolic starter baseline, not a Git SHA. It represents a partially working single-tenant legacy prototype with reservation revision 1, replay gaps and no production-safe settlement. Some target modules may exist as stubs or partial implementations. No actual HarborFlow repository or Git object is supplied. At future execution, bind B0 to the observed full target commit, inspect the actual source state and reconcile discrepancies before mutation. Do not invent a SHA or imply the source exists here. Existing tests at that baseline are evidence to inspect, not assumed green. The requested plan must state how it will become concrete against real source and accepted predecessor results.

The source inventory is authoritative for target paths, counts and intended direct static prerequisites. It does not prescribe a work schedule. Static prerequisites describe required modules/contracts, not necessarily separately accepted work units. Runtime and schema edges have different meanings, documented in the manifest. Resolve every dependency in the delivery plan without turning runtime mutual dependence into cyclic source imports or circular build prerequisites.

## Business requirements

A carrier intake message has tenant, stable source message ID, shipment ID, source revision, occurred time and payload. Retrying the same accepted message must return the same logical acceptance result. Identical source identity with conflicting content is quarantined with a reason; it must never overwrite accepted history. Bad tenant context fails before reading or modifying business data. Ingestion emits normalized shipment facts only after its transaction commits.

Inventory combines shipment and warehouse observations. Quantities are integers in explicitly named units; availability never becomes negative. Older source revisions cannot undo newer facts. A missing intermediate revision triggers bounded reconciliation while unrelated tenant aggregates progress. Reconciliation must not manufacture stock. Two concurrent reservations for the final available unit cannot both succeed.

Allocation deterministically ranks candidate stock, reserves capacity and assigns a monotonic fencing token. Reservations have a tenant-scoped stable ID, expiry and lifecycle revision. Cancelling or expiring a reservation must not release capacity already consumed by a successfully admitted dispatch. A network timeout after requesting dispatch is an unknown outcome, not proof that execution rejected the request. Recovery must reconcile that uncertainty before releasing or duplicating capacity.

Execution validates and, when appropriate, renews reservation authority through allocation, admits an idempotent dispatch, drives a fictional carrier adapter and reports accepted/completed/failed outcomes. Carrier calls can succeed while their response is lost. The carrier simulator supports lookup by idempotency key; recovery must use it. A lease holder with an older fencing epoch must never dispatch or finalize after a replacement holder takes ownership. Allocation consumes execution outcomes; execution consumes allocation reservation changes. Both services need the other at runtime. Neither implementation may statically import the other's modules, and startup must not require an unbounded synchronous callback chain. Other services must still boot and make progress while either service is unavailable.

Settlement consumes terminal execution facts and calculates charges using explicit tariff version and integer minor currency units. Ledger postings are balanced and immutable. Replayed or duplicated facts cannot produce a second charge. A correction uses a linked compensating posting; deletion or editing of committed financial history is forbidden. Mixed currencies cannot be netted silently. A cancellation arriving after financial posting must enter the correction path, not pretend rollback erased money movement.

## Shared state, events and recovery

Production uses one fictional relational database instance and one application schema shared by all five services. This is not a database-per-service exercise. Every tenant-owned primary/foreign/unique key, lookup and lock boundary must retain tenant identity. A fail-closed database isolation policy supplements explicit tenant predicates. Connection reuse must clear tenant session context on success, failure and pool return. A transaction cannot acquire an unbounded tenant-wide lock merely because one aggregate is busy. Shared adapters own persistence boundaries; services may not introduce private copies of the engine or divergent ledger/inbox rules.

A committed command must atomically write its aggregate revision, journal entry, inbox receipt and generated outbox events where applicable. Publishing before commit is forbidden. Broker delivery is at least once and may be delayed, duplicated or reordered; assume neither global ordering nor distributed exactly-once delivery. Every envelope contains tenant, event ID, producer, aggregate ID/version, schema revision, causation ID, correlation ID and occurred time. Preserve identities across retries. Consumers detect duplicates, reject conflicting identity reuse and handle gaps without silently applying dependent events in the wrong order. Cross-service consistency is eventual; local invariants are transactional. Explicitly identify authoritative states when observations disagree.

Transient retries have a finite attempt and elapsed-time budget, bounded backoff and a durable exhausted state. Poison messages retain tenant, causal context and reason without blocking the entire partition forever. Redrive requires an audited decision, preserves original identity and must not bypass business invariants. Outbox claims and worker leases need bounded duration, fencing and recovery after crash. Hot-tenant contention must not starve another tenant. Retention or checkpoint cleanup cannot discard journal data needed to verify a snapshot or recover unacknowledged work.

Replay the same canonical accepted command journal with the same policy versions to byte-identical canonical state and emitted effect identities. Snapshot lineage includes tenant/aggregate identity, engine format revision, journal boundary and digest. Detect truncation, wrong lineage and corruption. Invalid snapshots must fall back to a verified recoverable journal where available, otherwise stop that aggregate visibly; never guess a state. Recovery cannot repeat an external dispatch or financial charge merely because the engine itself replayed effects.

The manifest declares four numbered migrations and eleven TypeScript adapters. `migration_after` orders SQL application; `schema_requires` names adapter runtime prerequisites. Migration 0003 is an additive reservation expansion. New and old applications must coexist while a bounded backfill runs. Backfill is resumable, tenant-scoped and detects concurrent updates. Migration 0004 is irreversible legacy cleanup and carries `deployment_requires: ["reservation-v1-retired"]`. That gate means all producers/consumers have compatible revisions, old application instances and queued revision-1 work are retired or translated, backfill and restore rehearsal passed, and the declared rollback window has expired. Do not promise an old-binary rollback after dropping its required columns. Migration ordering and application release compatibility must be expressed separately from import ordering.

Each concurrent future implementation/check assignment needs isolated mutable state. For this exercise, a full product test environment uses a distinct database instance and schema per worktree, broker namespace, carrier simulator state, ports, output directory and logs. The five services inside that environment still share its one application schema. A shared integration environment is exclusive to its owning check; never let parallel workers mutate it. Read-only planning does not need fabricated service infrastructure. Show resource ownership and cleanup responsibility when future execution would need them.

## Observable acceptance cases

These are required future checks, not checks already run. Auxiliary test paths and fixtures are for the planner to name. Keep evidence recoverable and distinguish isolated component checks from real shared-schema/service integration.

- Submit one tenant's intake message 20 times, including after a lost response. Observe one accepted journal transition and one logical normalized event; conflicting content with the same identity is quarantined.
- Use the same shipment, event and reservation IDs in two tenants. Attempt cross-tenant reads, references and writes, including connection reuse after a forced exception. Observe complete isolation and no pooled-context leakage.
- Deliver source revisions 3, 1, 2 and duplicate 3. Observe the agreed gap handling and eventual correct latest state, with no stale overwrite. A poison message reaches its bounded terminal queue while an unrelated valid aggregate proceeds.
- Race two requests for the last stock unit; at most one wins. Simulate a high-contention tenant with 100 competing requests and a second tenant with ten independent requests. The second tenant completes within a fictional 5-second test budget on the declared fixture environment; record environment assumptions instead of presenting this as measured capacity.
- Lose allocation's dispatch-request response after execution commits. Expire the reservation concurrently with execution's outcome. Observe exactly one authoritative terminal dispatch, no capacity double release and a recoverable pending outcome.
- Pause a lease owner, let a replacement acquire a higher epoch, then resume the old owner. Its writes and carrier actions are rejected. Repeat around carrier success with a lost response; lookup resolves the uncertainty without a second carrier operation.
- Kill each service between database commit and publish, and between message handling and broker acknowledgment. On restart observe eventual publication, duplicate-safe consumption and no lost committed transition.
- Replay 1,000 accepted commands containing out-of-order delivery, expiry and corrections twice from an empty state and from a valid snapshot. Canonical states/effect IDs match. Corrupt the snapshot digest and truncate its referenced journal independently; recovery either verifies a safe fallback or fails visibly for only the affected aggregate.
- Mix old and new reservation applications during migration 0003/backfill, force an interruption and restart it, and prove old/new reads agree. Attempt migration 0004 before its gate; it must be refused. Exercise an old-binary rollback before retirement and a forward recovery/restore procedure after irreversible cleanup.
- Deliver completion twice, crash settlement after the ledger commit but before acknowledgment, and then deliver late cancellation. Observe one original balanced posting plus the required linked correction, with immutable original rows and no double charge.
- Stop allocation, then execution, separately during live traffic. Observe bounded retries, explicit readiness/degraded status and recovery without a startup deadlock; ingestion/inventory and already-authorized independent settlement work continue within their valid domain boundaries.
- In a full shared-schema environment, trace a shipment through all five services and recovery boundaries using correlation/causation IDs. Check that the committed database/event history proves the business outcome, rather than relying solely on successful HTTP responses.
