# Feature-sized execution

Root normally creates and consolidates plans. Use read-only exploration/research
when it reduces uncertainty; preserve specialist routing and model/effort rules.
Choose boundaries by independently verifiable public results, manageable scope
for one executor, useful parallelism and dispatch/context/integration cost.
Group small features sharing files, contracts and acceptance. Preparation useful
only to one feature stays inside it; a reusable capability may be a predecessor.
Repeated private handoffs, cross-branch edits or mostly waiting executors indicate
a poor cut. Combine coupled work or extract a real foundation; never repair a
cycle by exposing another plan's internal phases or tasks. No fixed plan count,
phase count or file count determines decomposition.

Each implementation plan has one executor, feature branch and separate worktree.
The executor performs implementation itself, using internal phases and only the
explicitly granted read-only exploration/research children. Root owns shared Git,
acceptance, integration and target updates. A senior's general spawn authority
does not authorize implementation children in a plan-executor assignment.
Declare that executor once at plan level; internal implementation tasks belong to
it without subagent labels. Internal `(Subagent Task: <subagent_type>)` labels
reserve actual delegated reads for allowed exploration/research children.

The whole-plan dependency DAG is authoritative. A predecessor must be complete,
checked, verified, Root-accepted and integrated before its consumer starts. Bind
accepted public outputs/contracts/evidence to an exact commit. Consumers neither
name nor inspect predecessor phases, tasks or intermediate checkpoints. Root may
inspect all plans for coordination; it passes only public predecessor results.
Internal recovery/compaction checkpoints never release a dependent plan and need
no intermediate Contract 2.0 message. A join waits for named whole-plan results;
it is not an empty plan. An integration plan needs substantive implementation or
testing with its own result and acceptance criteria.

Root keeps a compact work-order index referencing authoritative plans/inventories:
plan IDs/paths, public inputs/outputs, whole-plan predecessors, executor,
branch/worktree, ownership/resources, baseline/result commits, completion,
acceptance/integration state and target expected tip. Do not duplicate it in a
nested master phase plan. Before dispatch, check graph references/cycles,
exclusive concurrent ownership, isolated resources, accepted predecessor identities
and management's executor/helper/runtime capacity. Use the complementary
[whole-plan validator](whole-plan-validation.md); it does not inspect Git or prove
acceptance. Keep intra-plan file/task dependency evidence separate and opaque.

Serial successors may own the same paths only after the predecessor is inactive,
accepted and integrated, with explicit ownership transfer and a new accepted
baseline. Shared interfaces have one active owner; mutable resources, outputs
and logs are isolated. Interruption may resume the same plan/branch only through
explicit continuation and capacity checks. Replacement requires inactivity and
explicit exclusive transfer of scope, evidence and responsibility.

Assume a healthy main unless evidence disproves it. Plan result checks establish
the feature/public contract; Root verifies its frozen scope. Separate executor
scope-local QS and terminal prerequisites from subsequent Root-owned review,
acceptance and integration gates. Record those Root actions explicitly; a plan's
executor never waits for its own Root acceptance/integration before delivering its
terminal result. Whole-plan consumers still wait for the accepted integrated
predecessor result. Merge checks address
affected interactions, intervening target changes and conflict repairs, reusing
applicable evidence conditionally. They do not automatically repeat the full suite.
After all plans are integrated and writers inactive, the exact integrated result
requires whole-task/system checks and final frozen independent review. See
[parallel-git.md](parallel-git.md) for merge evidence and guarded updates.
Final-gate failure keeps the work order open: assign bounded repair, rerun affected
checks and the full final gate on the corrected candidate. If main is unhealthy,
separate pre-existing from introduced failures and pause affected successors while
independent work may continue. Existing commit/approval rules remain binding;
this workflow invents no checkpoint exception or publication permission.
